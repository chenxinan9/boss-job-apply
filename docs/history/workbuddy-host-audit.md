# WorkBuddy 宿主接入审计与交付状态

日期：2026-10-14。范围：v0.3.3 源码、现有测试与使用者提供的运行截图。未接入远端电脑，不公开截图、私人条件或日志。截图中的客户端解释是自报，未经原始工具证据验证，不直接认定为根因。

## 结论

当前公开包未满足独立下载、本人配置、真实首次沟通的交付标准。Windows WorkBuddy 已有零外发失败反馈；暂不推荐普通使用者继续试跑。原 Codex / macOS 的原生浏览器工作流、WorkBuddy / macOS 的 Ego 路径与 Windows Agent Browser 路径不同，前两者的历史成功不能替代后者验收。没有同环境对照，不能把失败归因于模型档位。

## 文件证据与失败路径

1. 两包 `scripts/browser-session.mjs` 的 `main()` 会在任何 `AGENT_BROWSER_*` 环境变量存在时拒绝执行。复现入口：在不含私人数据的临时目录设置 `AGENT_BROWSER_ARGS` 后执行 `node /技能绝对路径/scripts/browser-session.mjs get url`，会在启动浏览器前报冲突。保护防止环境覆盖固定配置，但尚不支持宿主必要参数；不能通过清空宿主环境来宣称修好。
2. 原 `references/agent-browser.md` 允许冲突后改用宿主原工具，未要求这是已验证会话。反馈中执行者自报实际走了这个分支；因此后续运行已经不是固定入口的覆盖范围。main 文档现已区分继续使用正常原生会话与绕过失败入口另造控制通道。
3. `tests/browser-session.test.mjs` 与 `tools/browser-smoke.mjs` 都过滤测试进程中的全部 `AGENT_BROWSER_*`。单测只证明环境冲突会被拒绝，中性页测试只证明干净配置下的跨进程连续性；`.github/workflows/portable-package.yml` 没有启动真实 WorkBuddy 宿主。三系统 CI 不是宿主兼容验收，不能据此恢复推荐。
4. 反馈中截图连接超时、标签消失的解释先后变化，缺少相应原始事件。空白页和 HTTP 200 无法区分目标选择、控制连接、页面关闭与认证问题。文档已明确不得在这些情况下反复请求登录或手动新建标签。

## 本次修正与未修复项

首页和安装页将未交付状态放在下载入口之前，Release 说明同步公布已知失败；源码手册修正环境冲突和连接失败的处理。不更换候选人的资料、评分或条件，不增加投递驱动/数据库/定时任务，不改写已发布 ZIP 或原校验和。本次是交付状态与失败处理纠偏，不声称已修复 Windows 控制链路。

宿主兼容修复仍需要在真实 Windows WorkBuddy 中确认实际工具版本、宿主参数用途以及同一控制会话的失败动作。不得收集认证信息、完整环境变量值、简历或整份聊天。不能从截图猜出参数后直接放行。

## 恢复推荐的必要证据

- 在实际宿主保留必要设置，独立下载候选并保留本人配置；全程使用同一已确认控制入口，跨调用仍能读取原目标。
- 本人完成必要登录后原页继续，可靠读出本人筛选需要的字段，并实际切换卡片/JD。
- 本人授权后由 WorkBuddy 自己完成真实首次沟通；作者不途中补操作提示、代点或修改验收目录来促成通过。
- 记录准确系统、客户端/工具版本和验证范围；点击派发、首次沟通成功、平台满额分开表述。无需投满作为这次交付验收门槛。

## 官方依据

[Agent Browser 配置优先级](https://agent-browser.dev/configuration)说明环境参数高于配置文件，因此不能忽略宿主设置。[MDN Window.close](https://developer.mozilla.org/en-US/docs/Web/API/Window/close)说明关闭限制与窗口创建方式、历史等有关；它并不证明某个 BOSS 页面调用过 close，也不能证明手动标签一定不会关闭。
